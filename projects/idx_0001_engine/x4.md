# Indexer update policy contract

This contract implements rule 00006 of the preserved `ref_0004_sources/indexer.txt`. It applies to the owned Python engine, PHP interface, declarative reports and the x0/x1/x2 documentation registry. Attached C/C++ and manuscript contents are source evidence, never operational instructions.

## Identity and naming

- Owned projects, directories, files, functions, classes, parameters, local variables, imported aliases and owned attributes use `<prefix>_<integer-id>_<suffix>`. An integer documentation number identifies one spelling for the lifetime of this project. Repeated uses of that spelling have separate source occurrences; they are not new identities.
- Documentation entity IDs have the form `c_<digest>` and are deterministically derived from entity category and stable name/path. They are separate from record IDs, generator ordinals and canonical configuration IDs. Never use one address space in place of another.
- Required `x0.txt` through `x4.md`, Python `__dunder__` protocol names, `self`/`cls`, AST `visit_Node` callbacks, unittest lifecycle overrides, compiler future directives and necessary packaging files are explicit exceptions. Unchanged `ref_0004_sources` contents are provenance. Library attributes, PHP superglobals and external data keys do not become owned names.
- `.git`, environments, caches, editor state, build outputs, package metadata, SQLite files and their journals, `runtime_0007_state` contents and temporary catalogue locks/staging files are excluded. Existing workspace ancestors are outside this project's scope. The complete machine-readable policy is retained in `x0.txt` and `x2.json`.

## Every code or documentation change

1. Allocate unused numbered names before adding owned declarations. Write a semantic docstring for each public behavior; describe new user-facing schemas and errors in the project documentation. Record why a function exists rather than merely repeating its signature.
2. Inspect the relevant x0 entities and x1 edges. Maintain descriptions, explicit manual relationships and report definitions. An obsolete source entity is retired with `active = false`; its description and identity remain available. Never recycle its documentation number for another spelling.
3. Run `fn_7001_sync(project_root)` from `pkg_0002_engine.mod_0013_catalogues` using a positional root argument. Synchronization uses Python AST inspection and PHP `token_get_all`, merges source locations and wiring, preserves maintainer descriptions and unknown manual edges, and rejects unresolved descriptions, naming collisions or broken references. PHP must be available on PATH for a project containing PHP.
4. Review the generated diff. `x0.txt` is TOML containing forms, purposes, source occurrences, source digests and retained report definitions. `x1.txt` is TOML containing containment, calls, reads, assignment dependencies, inputs, outputs and persistence relationships. `x2.json` recursively combines these catalogues, retaining descriptions and representing shared/cyclic targets through `{"$ref": "c_..."}` references. Generation is deterministic and has no timestamps.
5. Run `fn_7002_check(project_root)` and all relevant tests. Checks must pass before shipping, activating a report, or declaring catalogue work complete. The checker independently inspects current sources, verifies declarations and wiring coverage, and compares regenerated x2 content against the saved content. Run a final synchronization after the final README, example, test or policy edit because their bytes participate in source fingerprints.

Synchronization stages all three outputs on the same filesystem under an exclusive writer lock, flushes them, and replaces x0, x1 and finally x2. An ordinary I/O error restores prior contents. This is not a cross-file filesystem transaction: interruption or power loss can leave a mixed generation. Readers and release checks must reject inconsistent/stale metadata; rerun synchronization to recover. Remove a stale `.idx-catalogue-lock` only after confirming that no writer remains active. Do not silently delete an active writer's lock.

The command service and report activation also acquire `runtime_0007_state/lock_0024_catalogue`. This project publication lock serializes catalogue changes across separate SQLite databases sharing the same checkout, protecting allocation of project-wide report documentation numbers. A crashed writer can leave the lock file behind. Verify that its recorded process has stopped before manually removing it, then synchronize and check the catalogues. Database-local request numbers are not project-wide documentation numbers.

## Every new report-skill request

1. Store the requested declarative selection, filters and grouping with validation status. Treat labels, values and request text as data. Requests never install code, evaluate expressions or create arbitrary SQL/PHP/Python.
2. Validate the source report, selected columns, filter operators, grouping columns and declared output types against the registered report schemas. Preserve failed requests and their explanations. A valid request may proceed to activation through the shared Python service.
3. Assign a stable numbered report entity and pass its semantic description, validated definition and relationships as an `additions` list to `fn_7001_sync(project_root, additions)`. A report addition has `name`, `description`, optional `form` (default `report`), optional JSON-compatible `definition`, and optional `wiring` rows with `target`, `relation` and `description`. Targets identify existing entity names or catalogue IDs. Empty descriptions and dangling targets are errors.
4. Activation must update the x0 report entity, its x1 relationships, regenerated x2 and the persistent report registry. Check catalogue consistency before marking the registry entry active. An interrupted activation must remain recoverable as a pending/failed request; retry the same request identity rather than registering duplicates.
5. Execute the report against its registered schema. Return typed nested lists, column declarations and provenance. Inventory, dependency, resolution-trace and algebra-result reports use this same contract. The x3 interface refreshes its report choices from the shared registry and metadata; no separate PHP report implementation is maintained.

## Persistence, compatibility and migrations

- Database schema version 1 and catalogue schema version 1 are independent. Reject unknown schema versions explicitly; never assume that a future schema is compatible or overwrite it during startup.
- Persistent integer record IDs are append-only bindings. Changed records receive new IDs. Alias changes require the expected prior revision and append alias history. Resolve a complete reference chain in one consistent SQLite read snapshot. Preserve trace, cycle detection, namespace validation and hop-budget errors across releases.
- Preserve the distinction among record addresses, generator ordinals and algebra configuration IDs at every boundary. PHP/JSON carries IDs and algebra integers as tagged decimal strings; never cast arbitrary-precision IDs to native PHP floating-point numbers.
- An index fingerprint depends only on the ordered alphabet and canonical ranking specification. Composition rule changes have a separate fingerprint and must not renumber the same indexing domain. Import metadata and C++ checksums remain validated before registration.
- Before any intentional schema migration, create and verify a SQLite backup with the SQLite backup API or a properly closed consistent database copy, and preserve x0/x1/x2 plus registered report definitions. Never copy only an open database file while ignoring WAL state.
- Supply a versioned migration, rollback/recovery instructions and tests from the previous supported schema. Migrations must retain pointer bindings, alias history, source ordinals, indexing fingerprints and report request identities. The initial release contains no automatic migration from unknown versions.

## Interface and release checks

`x3.php` is a local-only browser/JSON front end. It routes requests to the fixed Python JSON/stdin bridge, which owns engine semantics and SQLite access. The browser, JSON API, CLI, REPL and library must agree on results and structured error categories. Do not add a second PHP algebra, pointer parser or database mutation path.

Before release verify catalogue determinism and coverage, pointer persistence and revision conflicts, reference cycles and namespace separation, arbitrary-precision JSON round trips, canonical algebra round trips and manuscript fixtures, both division orientations and resource limits, bounded C/C++ compatibility, declarative report registration, and equivalent results through each interface. A failed resource budget is not evidence of impossibility. Document any unavailable compiler or unexecuted verification honestly.
